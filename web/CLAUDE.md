@AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

The Symfony 8.x web app of the `AgentTools` monorepo: it stores Ingress agent stats, sent by the Android app (`../app`) via a Google-authenticated API, and lists them. It includes user management with the Google Identity Services login ("Sign in with Google" button). In `dev` there is also a form-based login.

## Commands

```bash
bin/install   # Full setup: composer install, Docker, migrations, Symfony server (no fixtures)
bin/start     # Start dev environment (Docker + Symfony server)
bin/stop      # Stop Docker containers
```

## Architecture

### Entities & Enums
- **`User`** (`system_user` table) — single entity, implements `UserInterface`. Uses `identifier` (unique string) as the username. `googleId` is nullable. Role is stored via `UserRole` enum.
- **`UserRole`** enum — `ROLE_USER` (default: users registered by a Google sign-in get it and upload agent stats and custom medals right away) and `ROLE_ADMIN`. `role_hierarchy`: `ROLE_ADMIN` > `ROLE_USER`. There was a `ROLE_AGENT` (an admin had to approve new users); `Version20261026140000` made its users `ROLE_USER`.
- **`User::$agentName`** — the Ingress agent name (nullable, unique, `[A-Za-z0-9_]`); uploaded stats must be for it. Without one, the first upload sets it from the stats' nickname (`AgentStatService`). Admins edit it in the user CRUD.
- **`User::$avatar`** — the Google profile picture (the ID token's `picture` claim) as a 100 px JPEG `data:` URI, as 4e-website's; `Service/AvatarUpdater` fetches it on a web sign-in and on API requests, only when the URL (`$avatarSource`) changed and only from `*.googleusercontent.com`; a failure keeps the old one. Others see it with the avatar part (`User::getVisibleAvatar()`). In `test` the HTTP client is mocked (`tests/Fake/GooglePictureResponses`, `FakeGoogleIdTokenVerifier::token(picture: …)`).
- **`User::$visibleParts`** — the `ProfilePart`s (enum: agent, avatar, latest stats, stats history, custom medals, Bannergress, labelled "Banners") other signed-in users see; JSON, private (`[]`) until the user saves the form on `/profile` (`User::$visibilityChosenAt`). `User::isVisible()`: the other parts only count with the agent part and an agent name. `EventListener/ChooseVisibilityListener` sends a web sign-in (`main` firewall) to `/profile` while `visibilityChosenAt` is null; the app asks when `GET /api/me` says `visibilityChosen: false` and saves them with `PATCH /api/me` `visibleParts`.
- **`User::$bannergress`** — what the app synced from Bannergress (JSON, null until then; `ApiResource/Bannergress`): the number of banners published (with a mission by the agent), on the to-do and done lists, every published banner, the newest 20 to-do banners (id, title, missions, picture relative to `https://api.bannergress.com`) and `syncedAt` (set by `MeProcessor`). Bannergress answers only signed-in users and its sign-in only redirects to bannergress.com, so only the app can read it. The sync's whole done list (`doneBanners`, written only) goes to **`DoneBanner`** (`Bannergress/DoneBannerSync`: new ones added, gone ones removed, the day kept; an event banner without a day gets the event's first day, the app sends `eventStartDate`): `bannerId`, title, missions, picture, `position` and `doneAt`, the day the user did it (web: `Controller/Banners/DoneAt`; API `PATCH /api/done-banners/{id}`, own only, `DoneBannerVoter`); banners with a day are on the timeline (kind `banner`). Pages (titled "Banners"): `/banners` (own, `Controller/Banners/Index`) and `/agents/{agentName}/banners` (`Read`, with the Bannergress part), a world map with a dot where each banner starts (`Bannergress/BannerMap`, `banner_map_controller.js`: Leaflet from the import map, OpenStreetMap tiles, dots in the timeline's colors `--banner-published|done|todo`, the legend toggles filter the lists; banners synced before the start points were added are counted as missing) and an accordion published / done / to-do (`templates/banners/`; `accordion_hash_controller.js` opens the section of a `#done-banner-{id}` link); the user menu link is "My banners" (the navbar has only Agents and Admin); `/agent-stats` and `/agents/{agentName}` show the counts (`agent_stat/_banners.html.twig`), `GET /api/agents/{agentName}` has `bannergress` and `doneBanners`.
- **`User::$customMedals`** — the custom medals (anomaly, annual, event) recognized by the app, as 4e-website's `Agent::$custom_medals` (JSON, `{}` by default). The anomaly seasons (`MedalChecker::ANOMALY_SEASONS`) are stored under `anomaly` but shown in their own "Anomaly season" section (`CustomMedal::section()`, `CUSTOM_MEDAL_SECTIONS`), as in 4e-website and Ingress.
- **`TimelineEvent`** — a custom event on the user's timeline: `date` (`Y-m-d`), an optional `endDate` (an event over several days, e.g. a travel; not before `date`; travels cannot share a day: `Validator/NoOverlappingTravel`, `TimelineEventRepository::findOverlappingTravel()`, 422 / form error on `endDate`) and `text` (≤ 500), owned by a `User` (set by the form's controller or `State/TimelineEventProcessor`). API resource `/api/timeline-events` (own only via `Doctrine/AgentStatOwnerExtension`, newest first; `POST`, `PATCH`, `DELETE` for the owner, `Security/Voter/TimelineEventVoter`). Others see the events with the stats history part.
- **`AgentStat`** — Ingress all-time stats with the columns of 4e-website's `agent_stat` (same names), owned by a `User` instead of an Agent. Unique per owner + `datetime`; `AgentStatService` throws `StatsAlreadyAddedException` (API: `409`). Also the API Platform resource (see API below); `#[SerializedName]` gives the stats their column names, `owner` and `getStats()` are `#[Ignore]`d. Input: `AgentStatInput`, keyed by column name (`#[SerializedName]` for the snake_case ones).

### Controllers
Single-action controller pattern under `src/Controller/`:
- `User/` — CRUD (Index, Create, Read, Update, Delete), each in its own class. Index (`/admin/agents`, Admin → Agents, "Admin agents"; the CRUD is under `/admin/agents` too) is also the admins' agent list: every user with picture (also a private one), agent, role, the privacy settings as `ProfilePart::icon()` icons and level (as the app's Admin agents)
- `Security/` — `GoogleIdentityController` (the route `GoogleIdentityAuthenticator` handles) plus `LoginFormController` and `Logout`
- `System/` — `AboutController`, `LogviewController`
- `AgentStat/` — the user's agent stats: Index (latest stats, medals, the Bannergress counts and the timeline's counts, `_timeline_summary.html.twig`), Timeline (`/agent-stats/timeline`, the own timeline with the form for a new event), Read (owner only, `AgentStatVoter`), Import (`/agent-stats/import`, user menu → Import stats). Stats come in through the API (the app), or as a CSV file: `Import/AgentStatCsvImporter` reads a header row of agent_stat column names, as 4e-website's export (Migrate → Export CSV), and saves each row like the API (`AgentStatInput`, validation, `AgentStatService`: duplicates skipped, other agents' stats reported); unknown columns are ignored, rows without nickname/faction (4e's before May 2020) get the user's agent name and the file's first faction; a `.json` file is custom medals (4e's Migrate → Export custom medals), `Import/CustomMedalsJsonImporter` merges them with the user's, keeping the higher tier, and reports medals or tiers it does not know. A big CSV file would run into the server's time limit, so with JavaScript (`stats_import_controller.js`, a progress bar) it is imported in parts: `ImportStart` (`POST /agent-stats/import/start`, the form, JSON) keeps the file in `var/imports/{env}` (`Import/CsvImportJob`, the progress in the session, unfinished files removed after a day), each `ImportNext` (`POST /agent-stats/import/{import}`, 32 hex digits, the owner's only, else 404) imports the next `CsvImportJob::BATCH` (100) rows (`AgentStatCsvImporter::import($owner, $csv, $offset, $limit)`; the saved stats are detached, else each row's flush checks every row before it); the last one sends the chat message and adds the flashes (`Import/ImportFlashes`, also used by `Import`) and answers where to go. Without JavaScript the form imports the whole file at once
- `Agent/` — other agents' profiles (`ROLE_USER`): Index `/agents` (`UserRepository::findVisibleAgents()`, filtered in PHP because the parts are JSON, for everyone; rows from `agent/_agent.html.twig`), Read `/agents/{agentName}` (ignoring case; `404` without the agent part) shows only the visible parts, the stats history as the timeline's counts (`_timeline_summary.html.twig`, `TimelineEntry::counts()`, as the own `/agent-stats`), Timeline `/agents/{agentName}/timeline` the agent's timeline, read-only (`404` without the stats history part)
- `TimelineEvent/` — Update (`/timeline-events/{id}/edit`) and Delete of the own events (`TimelineEventVoter`); new events are added with the form on `/agent-stats/timeline` (`AgentStat/Timeline`, `Form/TimelineEventType`); both go back there
- `Events/` — Index `/events`, public: the calendar of Ingress events (see Ingress events below); in the navbar
- `History/` — Index `/history/{slug}`, public: the documents of `../docs/events/` (see History below); in the navbar
- `Links/` — Index `/links`, public: the Ingress link list of `../docs/links.md` (see Link list below); in the navbar (not the user menu: it is not the user's own)
- `ProfileController` (the visibility form `Form/ProfileVisibilityType`), `DefaultController`

Keep controllers at most one directory below `src/Controller/`: `ControllerAccessTest` (from `elkuku/symfony-utils`) cannot resolve deeper namespaces.

Access control uses `#[IsGranted()]` attributes.

### API (API Platform)
JSON-LD under `/api`, docs at `/api/docs`, paths with dashes (`path_segment_name_generator`). Used by the Android app (`app/` in the monorepo); keep `app/.../data/StatsApi.kt` in sync.
- `AgentStat` (`#[ApiResource]` on the entity) — `GET /api/agent-stats` (own stats only via `Doctrine/AgentStatOwnerExtension`, newest first, paginated), `GET /api/agent-stats/{id}` (`AgentStatVoter`), `POST /api/agent-stats` with `AgentStatInput` → `State/AgentStatProcessor` → `AgentStatService`. `StatsAlreadyAddedException` → `409`; type errors are collected as `422` violations.
- `ApiResource/Me` — `GET /api/me` via `State/MeProvider` (id, identifier, role, agent name, custom medals, `visibleParts`, `visibilityChosen`); `PATCH /api/me` (`ROLE_USER`, `application/merge-patch+json`, `State/MeProcessor`) sets the agent name, the custom medals, the visible parts (counts as chosen) and the Bannergress sync (`bannergress`, replaced as a whole), the only writable fields (serialization groups `me:read` / `me:write`; `read: true` because `/me` has no URI variables). The agent name is `User::$agentName`, unique ignoring case (`UserRepository::findOneByAgentName()`; taken → `422` violation). `POST /api/agent-stats` answers `422` (`AgentNameException`) for stats of another agent (`AgentStatInput::$nickname`, compared ignoring case); without an agent name it sets it to the nickname, `422` if that is no agent name or another user has it (also when another upload takes it at the same moment: a unique violation other than `agent_stat_owner_datetime`).
- `ApiResource/CustomMedals` — not a resource of its own: `Me::$customMedals` (`GET /api/me`; `PATCH /api/me`), the user's custom medals in 4e-website's format (`{"anomaly": {"orion": "platinum"}, "annual": {"voyager": 5}, "event": {…}}`), stored in `User::$customMedals` (JSON). A `PATCH` is a JSON merge patch: it replaces the groups it sends and keeps the others (the app sends all three); null keeps the agent name or the medals. Only the key/tier format is validated (the medal list lives in the app's `data/CustomMedals.kt` and in `Medal/MedalChecker`).
- `ApiResource/Agent` — `GET /api/agents` and `GET /api/agents/{agentName}` (`ROLE_USER`, `State/AgentProvider`), the app's version of web's `/agents` pages: only agents with the agent part, and only the parts they show (null otherwise). The list has agentName, faction, level, avatar; an agent also latestStats and history (stats rows as `/api/agent-stats` has them, without the id) and customMedals (`CustomMedals`, group `agent:item`). `404` for a private agent.
- `ApiResource/UserPrivacy` (short name User) — `GET /api/users` (`ROLE_ADMIN`, `State/UserPrivacyProvider`): every user with identifier, role, agent name, faction, level, avatar (also a private one) and `visibleParts` / `visibilityChosen`; the app's Users list for admins.
- `ApiResource/LinkList` — `GET /api/links` (public, `State/LinkListProvider`, `Cache-Control: public, max-age=3600`): the link list's sections (`LinkList/LinkSection`: title, links of `LinkList/Link`: title, url, description or null); the app's Links screen.
- Errors are `application/problem+json` with `detail`; `GoogleApiTokenAuthenticator`'s `401` uses the same shape.
- `/profile` (no form) shows admins an API token for the docs' Authorize button: `ApiTokenStore` keeps the Google ID token of a web sign-in (`GoogleIdentityAuthenticator`) in the session; in dev with `APP_FAKE_GOOGLE_TOKENS` a fake token for users with a `googleId`.
- `ApiResource/IngressEventList` — `GET /api/events` (public, `State/IngressEventListProvider`, `Cache-Control: public, max-age=3600`): `events` (`IngressEvents/IngressEvent`) and `generatedAt`; the app's Events screen. Nulls are left out of the JSON.
- `ApiResource/History` — `GET /api/history/{slug}` (`anomalies` or `mission-days`; public, `State/HistoryProvider`, `Cache-Control: public, max-age=3600`): a document's `title` and `blocks` (see History below); the app's History screen.
- Operations check their role themselves (`security:`): all but `GET /api/links`, `GET /api/events` and `GET /api/history/{slug}` need `ROLE_USER` (single stats via `AgentStatVoter`: own only). There is no `access_control` rule for `^/api/`, so `/api/docs` is public.

### Security
Multi-authenticator: form login (dev only) + `GoogleIdentityAuthenticator`, which verifies the ID token the Google Identity Services button posts to `/connect/google/verify` (with Google's double-submit `g_csrf_token` cookie and field, which must match; tests post with `tests/Fake/GoogleSignIn`). Remember-me is enabled.

Both Google authenticators use `GoogleUserResolver`: `identity()` requires `sub`, `email` and `email_verified` (an unverified email could otherwise link someone else's account), `resolve()` matches by `googleId`, then links by `identifier == email`, else registers a new `ROLE_USER`.

The stateless `api` firewall (`^/api/`) uses `GoogleApiTokenAuthenticator`: `Authorization: Bearer <Google ID token>`, verified against `OAUTH_GOOGLE_ID` (the Web client ID; the Android app uses it as `serverClientId`). It finds the user with `GoogleUserResolver` (like the web Google login). Token verification is behind `GoogleIdTokenVerifierInterface`; in `test` it is replaced by `FakeGoogleIdTokenVerifier` (`FakeGoogleIdTokenVerifier::token($googleId, $email)`).

Tooltips: elements with `data-tooltip` (heading) and `data-tooltip-body` get the site's styled tooltip (`tooltip_controller.js` on `<body>`, the card in `base.html.twig`, the chart tooltip's look), used for medals, C.O.R.E and Simulacrum instead of `title`.

### Timeline
`Timeline/TimelineBuilder` merges the stats uploads (each with what changed since the one before: AP, level, medal upgrades, recursion, as the app's `data/ImportResult.kt`) and the custom events, newest first; an event comes before the uploads of its day. `agent_stat/_timeline.html.twig` shows it, with a label per year before the year's newest entry (`.timeline-year`, with the travel's line in a travel over the new year; the filter hides it with its year's entries), on `/agent-stats/timeline` (editable; `/agent-stats` has only the counts, as the app's My stats) and `/agents/{agentName}/timeline` (with the stats history part, read-only; `/agents/{agentName}` has the counts). A travel is two entries (`TimelineEntry::$travelEdge`): its end, before the uploads of its last day, and its start, after those of its first, each with its day; the entries between are `inTravel` and a line in `--timeline-travel` runs beside the timeline from the end to the start (CSS `::after`, hidden with the Travels filter; the My stats count has each travel once). The entries have no links (the own timeline has buttons to edit or delete an event and to change a banner's day). Every entry shows its day in the page's language without the time (`format_date('medium')` from `twig/intl-extra`: Oct 22, 2026 / 22.10.2026). An upload shows its date and what changed (first upload, new level, recursion, medal upgrades), not the level, AP or AP gain: those are in the chart; uploads where only the AP changed are left out (`TimelineEntry::isListed()`). The filters are the app's (`timeline_filter_controller.js`, in the browser): the milestones (first upload, recursion) always, medals and new level toggle the uploads with those, events / travels / banners by kind, and a from–to date range (a travel counts on every day of it). The range is picked below the chart in a flatpickr calendar (import map; themed in `app.css` with `html`-prefixed rules because flatpickr's stylesheet loads later) where only the days with an upload can be clicked (`ComparisonChoice::uploadDays()` as `data-timeline-filter-days-value`: day → id and time with seconds; a dot, another color for several uploads); the other days are not flatpickr-disabled but `aria-disabled` and unclickable, because flatpickr's range cannot span disabled days. Range, view and chosen times are kept in the URL (`from`, `to`, `view=compare`, `compareFrom`, `compareTo`, `history.replaceState`). On the own timeline a toggle shows instead of the list what changed between two uploads (as the app's): the first upload of the range's first day and the last of its last day (all dates: the first and the latest), on a day with several uploads its times as buttons, a dropdown for more than 4, seconds where two share a minute, picked the other way round on one day swapped; the page with `compare=1&compareFrom&compareTo` (ids, `Stats/ComparisonChoice`: own uploads only, older first) renders only `agent_stat/_compare.html.twig`: `Stats/StatsComparer` → `StatsComparison` with `StatsDiffRow`s (a port of the app's `computeImportResult`), `_comparison.html.twig` with only the gains. The range also zooms the chart, as the app's: the page with `from`, `to` (Y-m-d) and `chart=1` renders only `_timeline_chart_frame.html.twig` (`TimelineChart::build(…, $from, $to)`: the uploads and events on those days, the AP axis for those uploads, travels cut at the plot's edges), which the controller swaps in. Above it `Timeline/TimelineChart` (server-side geometry) and `agent_stat/_timeline_chart.html.twig` draw an inline SVG: AP as a line with a dot per upload, single-day events as flags, events with an end date as bands, styled tooltips (`chart_tooltip_controller.js`: the marks' `data-tip-*`, also on keyboard focus; an upload's AP gain since the one before, also outside a zoomed range; `aria-label` with the old title text); the colors are CSS variables `--timeline-ap|event|travel` per theme (validated for contrast and color blindness), the app uses the same (`ui/TimelineChart.kt`). `GET /api/agents/{agentName}` has the events next to `history`. The app builds the same timeline (`data/Timeline.kt`).

### Ingress events
`Command/FetchEventsCommand` (`app:events:fetch`) writes `data/ingress-events.json`, or with `--output` another file. `.github/workflows/symfony-pages.yml` runs it every day and on every Pages build and publishes the result as `ingress-events.json` on GitHub Pages (job `events`, starting from the published file so an unchanged list keeps its `generatedAt`); the site is only built again by the daily run when the list changed, and when ingress.com fails the published list stays and the job `events-failed` fails the run. The website reads that file with `IngressEvents/IngressEventSource` (`INGRESS_EVENTS_URL`, empty in `test`), kept in `cache.app` for an hour; when Pages cannot be reached the last list loaded stays, else the committed `data/ingress-events.json`, tried again after 5 minutes, so new events need no commit or deploy. The committed file is only that fallback: refresh it now and then by hand. `IngressEvents/IngressEventCollector` reads this and next year's `{year}-q{n}-events` and `-md` pages of ingress.com/news (a 404 is left out, any other failure aborts and leaves the file) and the "… Season - Overview" pages found in the first news index pages, those only for quarters without a schedule page. `EventPageParser` reads the three formats, without `<del>` text (corrected dates), with `Dom\HTMLDocument` so production needs no dom-crawler; `EventDateParser` the date texts. An Anomaly has an entry per site. Entries like "Early May" are reported as warnings, not guessed, as is a page without events; the Daily Bounties are left out. First Saturdays and Second Sundays no page lists are added with `confirmed: false` ("Expected"). `IngressEventFile::save()` leaves an unchanged list alone (no `generatedAt` diff). `/events` (`Controller/Events/Index`, `events/index.html.twig`) is rendered on the server: `EventCalendar` builds a Monday-first month grid, `?month=Y-m` and `?day=Y-m-d` pick what is shown (an invalid one is ignored; the Today button links to the current day, as in the app), one-day events are dots, global events over several days a line; colors are `--event-*` in `app.css`, the same as the app's `ui/EventsScreen.kt`, whose grid is `data/IngressEvents.kt`. Titles stay English. Tests use `tests/fixtures/ingress-events.json` (`when@test` in `services.yaml`), so a new fetch cannot break them; `IngressEventFileTest` checks the committed file's format.

### History
`../docs/events/anomalies.md` and `mission-days.md` (the deploy has the whole repository; `srcExclude` keeps them off the VitePress site) list past events, with medals as images in the app's assets and flags as emoji. `History/HistoryParser` reads them with `league/commonmark` into blocks (`HistoryDocument`, `HistoryBlock`, `HistoryInline`: headings, paragraphs, lists, tables; text, bold, https links, medals; other Markdown is listed in `$problems`), so the app shows the same through `GET /api/history/{slug}` (`ui/HistoryScreen.kt`); `HistoryLoader` caches them per file mtime and size. `/history` shows a tab per document with links to the years; the documents stay English. `tests/History/HistoryFileTest` checks the real files, so `symfony-tests.yml` also runs on changes to them. Signed-in users mark a row as attended: `HistoryAttendanceResolver` gives each table row with one exact date under a year's heading (Anomalies: one row per site, columns Date, Site, Role; Mission Days: Date, City, Type) a `HistoryAttendance` (key, date, text), except events not held (cancelled, postponed, moved) and, when marking, future dates. `Controller/History/Attend` toggles a `TimelineEvent` with that `historyKey` (unique per owner); the app posts the same to `/api/timeline-events` (`historyKey` is only written on `POST`; a second post answers with the event). It is an ordinary event on the timeline, so deleting it there removes the mark, and others see it with the stats history.

### Link list
The Ingress link list is `../docs/links.md` (the deploy has the whole repository; changed with pull requests, live after the next deploy; `srcExclude` keeps it off the VitePress site). `LinkList/LinkListParser` reads the part between `<!-- #region list -->` and `<!-- #endregion list -->` with `league/commonmark`: `## ` sections of `- [Title](https://…) — Description` entries; other entries and text are left out and listed in `LinkList::$problems` (not in the API). `LinkList/LinkListLoader` caches the result in `cache.app` per file mtime and size (an empty list without the file). `tests/LinkList/LinkListFileTest` checks the real file, so `symfony-tests.yml` also runs on changes to it; `.github/workflows/links.yml` checks the links daily (lychee). Section titles and entries stay English; `templates/links/index.html.twig` shows a card per section, as the app's `ui/LinksScreen.kt`.

### Translations
English, German and Spanish (`enabled_locales`). Texts are translation keys in `translations/messages.{en,de,es}.yaml` (keep all three in sync; `debug:translation de --only-missing`), the app's own constraint messages are in `validators.{de,es}.yaml`. `EventListener/LocaleListener` picks the language: the `locale` cookie set by the navbar's language selector (`Controller/Locale/Switcher`, `/locale/{locale}`), else the browser's `Accept-Language`. Enum `label()`/`help()` return keys. Medal, stat and faction names stay English; the API answers in English.

### Database
PostgreSQL via Docker Compose. Doctrine ORM with migrations. Fixtures in `src/DataFixtures/` create one regular user and one admin.

### Slack and Telegram
`Notifier/ChatActivity` posts the site's activity (`ChatFeed::Activity`): a new user (`GoogleUserResolver`, not a linked account), a stats upload through the API (`AgentStatProcessor`, with the AP gain from `AgentStatRepository::findPrevious()`) and a CSV import as one message (`AgentStat/Import`); `app:demo-agents` posts nothing. The messages are sent on `kernel.terminate` / `console.terminate`; a failure is logged as a warning. In dev and prod (the `&chat_handlers` anchor), `monolog.yaml` sends errors (fingers crossed, without 400/403/404/405/422, `{placeholders}` filled in, deduplicated for 10 minutes; `StatsAlreadyAddedException` and `AgentNameException` are `#[WithLogLevel(NOTICE)]`, the user's mistakes) and the `deprecation` channel (deduplicated for a day) to `Log/ChatLogHandler`, one message per batch (`ChatFeed::Errors`); its failures go to PHP's `error_log`. Both build a `Notifier/ChatText` (text, bold, code, links), which `Notifier/ChatSender` renders per chat (Slack mrkdwn, Telegram HTML; the visible text is cut at 3000 / 4000 characters) and sends to the feed's Slack channel (`SLACK_CHANNEL`, `SLACK_ERRORS_CHANNEL`; `symfony/slack-notifier`) and Telegram chat (`TELEGRAM_CHAT_ID`, `TELEGRAM_ERRORS_CHAT_ID`; `symfony/telegram-notifier`); an empty channel or chat ID leaves that chat out, a failing chat does not stop the other. `app:slack:test` checks the token (Slack's `auth.test`), posts to both channels and explains Slack's error codes; `app:telegram:test` does the same for Telegram (`getMe`) and lists the chats the bot has seen (`getUpdates`) while a chat ID is missing or with `--chats`. Slack channels: `.env` prod's `agenttools-uploads` / `agenttools-errors`, `.env.dev` `agenttools-uploads-dev` / `agenttools-errors-dev`; Telegram channels (bot @IngressAgentToolsBot): `.env` prod's AgentTools Uploads / Errors (`-1004410760418` / `-1004428417850`), `.env.dev` the DEV ones (`-1003739709215` / `-1003842112207`), `.env.test` `-1001` / `-1002`; pictures in `../images/telegram/`. `SLACK_DSN` and `TELEGRAM_DSN` are `null://null` by default; tests read the messages with `getNotifierEvents()` (not queued ones; filter by `getTransport()`). Telegram's API has the bot token in the URL, which the HTTP client logs: `Log/BotTokenProcessor` (`#[AsMonologProcessor]`, every channel and handler) masks it as `bot***` in messages, context and extra.

## Environment Variables
Credentials go in `.env.local` (gitignored):
- `OAUTH_GOOGLE_ID` — the Google **Web** client ID: the login button's client and the audience of the API's ID tokens
- `SLACK_DSN` — `slack://BOT_TOKEN@default` (a Slack app's bot token with `chat:write`); `SLACK_CHANNEL` and `SLACK_ERRORS_CHANNEL` come from `.env` / `.env.dev` — see Slack and Telegram above
- `INGRESS_EVENTS_URL` — the published Ingress events (in `.env`, no secret); empty: only `data/ingress-events.json`
- `TELEGRAM_DSN` — `telegram://BOT_TOKEN@default` (from @BotFather); `TELEGRAM_CHAT_ID` and `TELEGRAM_ERRORS_CHAT_ID` come from `.env` / `.env.dev` — see Slack and Telegram above
